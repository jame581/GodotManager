# godman 1.4.0

## Global installs moved to `/usr/local/lib/godman` (Linux)

Global installs used to live in `/usr/local/bin/godman` — a directory with the exact
name the godman binary needs in `/usr/local/bin` for `sudo godman` to work. They now
live in `/usr/local/lib/godman`.

- The move happens automatically on the **first privileged run of a godman command that
  sets up its paths** — `list`, `doctor`, `install`, `fetch` and the like; for example
  `sudo ~/.local/bin/godman list` (see below for why the full path). `version` and
  `--help` do not trigger it, and neither does any run with `GODMAN_GLOBAL_ROOT` set. Unprivileged
  commands keep working in the meantime and still see your global installs.
- The global `godot` shim, and the `env.sh` it sources, are rewritten as part of the move
  so `godot` keeps working. Under a HOME-resetting sudo (the default on
  Fedora, Debian and Ubuntu) that `env.sh` is root's (`/root/.config/godman/env.sh`), the
  one the global shim was written to source. `godman doctor`
  now checks what the shim actually points at and tells you if it is broken; for a global
  install the fix is `sudo ~/.local/bin/godman activate <id>` (doctor prints the exact
  command for your machine).
- User installs that still sit in `~/.local/bin/godman` move to
  `~/.local/share/godman/installs` the same way.

**Breaking:** `GODMAN_GLOBAL_ROOT` is now a *prefix*, as it already was on Windows: the
shim goes to `<prefix>/bin` and installs to `<prefix>/lib/godman`. A value that used to
mean `/usr/local/bin` must now be `/usr/local`.

### When `sudo godman` says "command not found"

sudo only searches its own `secure_path` — on Fedora, Debian and Ubuntu
`/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin` — which never includes
`~/.local/bin`, where the installer puts godman. Until the migration
has run, `/usr/local/bin/godman` is also still a directory. Run godman by its full path:

```sh
sudo ~/.local/bin/godman list
```

After that, on most distributions (Fedora, Debian, Ubuntu) you can install the binary to
`/usr/local/bin` (`GODMAN_INSTALL_DIR=/usr/local/bin`, run as root) so that plain
`sudo godman` works. RHEL-family systems (RHEL, Rocky, Alma) leave `/usr/local/bin` off
`secure_path`: install to `/usr/bin` (the RPM package does) or keep using the full path.
Check yours with `sudo grep secure_path /etc/sudoers`. The remedies `doctor` prints use
the full path unless godman sits in `/usr/bin` (or `/usr/sbin`, `/sbin`, `/bin`), which
every default `secure_path` includes — so a godman in `/usr/local/bin` is still shown as
`sudo /usr/local/bin/godman …`, which works everywhere.

## Launcher entries for every install

- Every install now gets its own application-menu entry (a `.desktop` file on Linux, a
  Start Menu shortcut on Windows), named after its version and edition.
- `godman install --no-shortcut` skips it.
- `remove` and `clean` delete the entries they own.
- Installs made before 1.4.0 have no entry. `godman doctor` lists how many there are;
  `godman activate <id>` adds one (and makes that install the active one).
- **Windows:** `deactivate` no longer removes the Start Menu entry — it belongs to the
  install now, not to the active version. It still removes the desktop shortcut.

## Other changes

- New `godman version` command: prints the godman, .NET runtime and OS versions.
- `godman doctor` also reports:
  - a shim that points at a missing binary,
  - an active install whose directory is missing,
  - old install directories, and whether each one is safe to delete or still in use.
