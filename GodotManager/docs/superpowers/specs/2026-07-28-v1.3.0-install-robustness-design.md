# godman 1.3.0 — Install-Flow Robustness — Design

**Date:** 2026-07-28
**Status:** Approved, ready for implementation planning
**Baseline:** `v1.2.0` (tag == `main` == `bb89085`); 111 tests passing, 3 skipped

## Goal

A hardening release for the install flow. No new subsystems and no new platforms —
close the integrity, cleanup, and resilience gaps in the code path that downloads
and unpacks a Godot build, and clean up the surrounding drift.

## Motivation

Four defects in the current install path, all confirmed against `v1.2.0`:

1. **Temp archives leak forever.** `InstallerService.cs:376` creates the download
   target via `Path.GetTempFileName()`. Nothing deletes it — no `File.Delete` call
   anywhere in the codebase touches it. Every download permanently leaves a
   100–200 MB archive in the system temp directory.

2. **Failed extraction poisons the target directory.** `InstallerService.cs:73`
   creates `targetDir`, then `ExtractAsync` runs at line 86. If extraction throws,
   the partial directory survives with no matching registry entry, and the next
   attempt fails with "already exists. Use --force" — a dead end for the user.

3. **Checksums are computed but never verified.** SHA-256 is hashed during download
   (`InstallerService.cs:378-399`) and stored on the registry entry, but the only
   consumer is `ListCommand.cs:35`, which truncates it for display. A corrupted or
   tampered download installs silently.

4. **No retry and no resume.** A single `GetAsync`; any mid-transfer network drop
   fails the whole install and discards every byte received.

Plus two drift items: `GodotManager.Tests.csproj` lacks `<Nullable>enable</Nullable>`
(6 CS8632 warnings on every build), and CLAUDE.md points at a `manifests/j/JanMesarc/`
directory that has never existed in the repo.

## Upstream facts this design depends on

Verified 2026-07-28:

- `GodotDownloadUrlBuilder.cs:46,68` builds URLs against the
  `downloads.godotengine.org` redirector, which resolves to object storage —
  e.g. `https://godot-releases.nbg1.your-objectstorage.com/4.5.1-stable/Godot_v4.5.1-stable_linux.x86_64.zip`.
- That mirror does **not** serve `SHA512-SUMS.txt` (returns 403).
- `SHA512-SUMS.txt` **is** a GitHub release asset on `godotengine/godot-builds`:
  `https://github.com/godotengine/godot-builds/releases/download/4.5.1-stable/SHA512-SUMS.txt`
  — 29 entries for 4.5.1, standard `sha512sum` format (`<128-hex><2 spaces><filename>`).
- The filenames in that file match the redirector's resolved asset names exactly,
  so the resolved archive name is a valid lookup key.
- The sums are **SHA-512**; godman currently computes SHA-256.
- `GodotVersionFetcher.cs:22` queries `godotengine/godot` — a *different* repo from
  `godot-builds`, where the builds and sums live.

## Decisions

| Question | Decision |
|---|---|
| Verification strictness | Verify when sums are obtainable; **mismatch aborts the install**. When sums cannot be obtained (offline, `--url`, `--archive`, non-stable flavor), warn and continue. |
| Resume depth | Cross-invocation: partials persist in a managed cache dir and resume on a later `godman install` run. |
| Structure | Extract a new `Services/DownloadService.cs`; `InstallerService` keeps orchestration, extraction, and registry writes. |
| Release shape | One release, `1.3.0`. |

---

## 1. Paths

`AppPaths` gains one property:

```csharp
public string DownloadCacheDirectory { get; }   // Path.Combine(ConfigDirectory, "downloads")
```

Created in `EnsureDirectories()` alongside the existing directories. Because it hangs
off `ConfigDirectory`, it inherits `GODMAN_HOME` overriding automatically, so
`GodmanTestFixture` isolates it with no fixture changes.

## 2. `Services/DownloadService.cs` (new)

Sole responsibility: get bytes from a URI onto disk, resiliently, and report whether
they are trustworthy.

```csharp
internal enum ChecksumStatus { Verified, Unverified }

internal sealed record ChecksumSource(string Version, string Flavor = "stable");

internal sealed record DownloadOutcome(
    string FilePath,
    string ArchiveName,
    string Sha512,
    ChecksumStatus Status,
    string? UnverifiedReason);

internal sealed class DownloadService
{
    public Task<DownloadOutcome> DownloadAsync(
        Uri uri,
        ChecksumSource? checksums,     // null => not an auto-built URL
        Action<double>? progress,
        CancellationToken ct);
}
```

Dependencies: `HttpClient`, `AppPaths`, `DiagnosticContext` — the same shape as the
existing services. Registered in `Program.cs` beside `InstallerService`.

Two statuses rather than three: every non-`Verified` path (offline, `--url`,
`--archive`, sums fetch failed, filename absent from the sums file) reports
`Unverified` with a human-readable `UnverifiedReason`. One code path, one message shape.

## 3. Download cache layout

Under `<ConfigDirectory>/downloads/`, keyed by the first 16 hex characters of the
SHA-256 of the absolute request URI:

| File | Meaning |
|---|---|
| `<key>.part` | Incomplete transfer — its existence *always* means "not finished" |
| `<key>.json` | `{ url, archiveName, etag, totalBytes }` |
| `<key>.archive` | Fully transferred, awaiting extraction |

A `.archive` file is *complete*, not necessarily *verified* — an `Unverified` outcome
still produces one, because the user chose to continue. Only a checksum **mismatch**
prevents the rename, and in that case the `.part` file is deleted outright (§5).

## 4. Resume protocol

1. If `.part` and `.json` exist and the stored URL matches the request URI, issue
   `GET` with `Range: bytes=<partLength>-`, plus `If-Range: <etag>` when an ETag is known.
2. **`206 Partial Content`** → append to `.part`. SHA-512 state cannot survive a process
   boundary, so the existing partial is re-read from disk to rebuild the hash before
   appending. One extra local read, negligible against a network transfer. The re-read
   happens on *every* entry into this step, including in-process retries — always
   rebuilding from disk avoids two divergent code paths for the same operation.

   Progress reporting accounts for bytes already on disk: the percentage passed to
   `progress` is `(partLength + read) / (partLength + contentLength)`, so a resumed
   download starts partway along the bar instead of restarting at 0%.
3. **`200 OK`** → the server ignored `Range`, or `If-Range` failed because the asset
   changed. Truncate `.part` to zero and write fresh. This is correct handling, not an error.
4. **`416 Range Not Satisfiable`** → the partial is at or past the resource length.
   Discard `.part` and restart from zero.
5. On completion, verify (§5), then rename `.part` → `.archive`.

Retries wrap this entire sequence, so attempt *n+1* resumes from the bytes attempt *n*
landed. Transient failures are `HttpRequestException`, `TaskCanceledException` **not**
originating from the caller's `CancellationToken`, and HTTP 408, 429, and 5xx.
Three attempts with 1s / 2s / 4s backoff. HTTP 403 and 404 fail immediately without
consuming retries.

## 5. Verification flow

`InstallerService` passes a `ChecksumSource` only when the URI came from
`GodotDownloadUrlBuilder`. `--url` and `--archive` pass `null`.

When a `ChecksumSource` is present, `DownloadService` fetches:

```
https://github.com/godotengine/godot-builds/releases/download/{Version}-{Flavor}/SHA512-SUMS.txt
```

parses the `<128-hex>  <filename>` lines, looks up the resolved archive name, and
compares against the SHA-512 streamed during download.

- **Match** → `ChecksumStatus.Verified`.
- **Mismatch** → delete the archive and throw. Never a warning.
- **Fetch failure, or filename absent from the file** → `ChecksumStatus.Unverified`
  with a reason; the download remains usable.

The sums fetch gets a **single attempt with no retry**. It is a small request whose
failure is non-fatal by design, and retrying it would delay the install for no
benefit — the retry/backoff policy in §4 applies only to the archive transfer.

`ChecksumSource.Flavor` is always `"stable"` today, because `GodotDownloadUrlBuilder`
only constructs stable URLs (`GodotDownloadUrlBuilder.cs:14,46,68`). It is a parameter
rather than a constant so that adding beta/rc support later does not require reworking
this signature; implementers should not build any behavior conditional on other values.

`GodotVersionFetcher`'s use of the `godotengine/godot` repo is deliberately left
unchanged — unifying the two repos is a separate change with its own risk.

## 6. Registry change

`InstallEntry` gains two fields, and `Checksum` carries SHA-512 for new installs:

```csharp
public string? ChecksumAlgorithm { get; set; }   // null => legacy sha256; "sha512" going forward
public bool ChecksumVerified { get; set; }
```

Both additions are additive to the persisted JSON, and `System.Text.Json` ignores
unknown fields by default, so an older godman reading a newer `installs.json` still
works. Existing entries keep their SHA-256 values and read back with
`ChecksumAlgorithm == null`, which is interpreted as `sha256`. No migration step.

`ListCommand` gains a verified marker on the checksum column.

## 7. Extraction rollback

Deleting `targetDir` on failure would destroy a previously-good install whenever
`--force` is in play. Instead, extraction goes to a staging sibling under the same
install root:

1. Extract into `<installRoot>/.staging-<guid>`; run the Linux executable-permission
   pass there.
2. On success: if `--force` and `targetDir` exists, delete it; then
   `Directory.Move(staging, targetDir)`.
3. On any failure: best-effort `Directory.Delete(staging, true)`, then rethrow. The
   original install is untouched.

Staging is a sibling of the target under the install root, so the move is guaranteed
same-volume and cheap.

## 8. Cleanup ownership

- The `.archive` and `.json` pair is deleted after a successful install — best-effort,
  warning only under `--verbose`, per the existing convention.
- A user-supplied `--archive` file is never deleted.
- `clean` removes the entire downloads directory.
- `doctor` reports the downloads directory size and stale-partial count, so an
  abandoned 200 MB `.part` is discoverable.

## 9. Error handling

`Program.cs:68` currently routes **every** failure through `AnsiConsole.WriteException`
with a stack trace, including entirely expected conditions such as
`InstallerService.cs:70`'s "install directory already exists". A user who forgets
`--force` gets a .NET stack dump.

Introduce `Infrastructure/GodmanException.cs` for expected, user-actionable failures,
carrying an optional hint. `Program.cs` catches it and prints a clean `error:` line
plus a `hint:` line with a non-zero exit code. Every other exception keeps the existing
`WriteException` treatment — an unexpected exception genuinely does want a stack trace.

Sites addressed:

| Site | Problem | Fix |
|---|---|---|
| `InstallerService.cs:70` | "already exists. Use --force" — dead end; doesn't say whether a registered install owns the directory | Report whether a registry entry owns it; offer `--force` vs `godman remove <id> --delete` |
| `GodotVersionFetcher.cs:156` | "Failed to fetch releases from GitHub: …" — no recourse offered | Distinguish rate-limit from offline; mention the stale-cache fallback and `--no-cache` |
| `InstallerService.cs:83,213` | Internal invariants leaking to users | Leave as unexpected exceptions — these firing means a bug |
| `ActivateCommand.cs:75,80,133,148`, `CleanCommand.cs:100,115` | Already clear and actionable | Unchanged |

New failure modes get first-class messages:

- **Checksum mismatch** — names expected and actual hashes, the sums URL, and states
  that the archive was deleted.
- **`Unverified`** — an always-on warning, not `--verbose`-gated. A skipped integrity
  check is moderate-risk, matching the precedent recorded in PLAN.md:112.
- **Rollback** — states that the original install was left intact.

## 10. Testing

`MockHttpHandlers` gains three reusable capabilities:

- `Range`-aware responses returning 206 with a correct `Content-Range`
- a mode that deliberately ignores `Range` and returns 200
- sequenced responses, so "fail twice then succeed" is expressible

New `DownloadServiceTests`:

- resume sends `Range: bytes=<n>-`, and the completed file matches the full expected content
- server returns 200 despite `Range` → partial truncated, result still correct
- 416 → discard and restart
- transient 5xx twice then success → one `DownloadOutcome`, backoff honored
- 404 → fails immediately, no retries consumed
- sums match → `Verified`
- sums mismatch → throws, **and** the archive file is gone
- sums fetch fails → `Unverified` with a reason, download still usable
- `null` `ChecksumSource` → `Unverified`, and no request is made to the sums URL

`InstallerServiceIntegrationTests` additions:

- extraction failure leaves no `.staging-*` directory and no `targetDir`
- extraction failure under `--force` leaves the pre-existing install intact
- successful install removes `.archive` and `.json` from the download cache
- a user-supplied `--archive` file still exists after install

One E2E test: install with mismatched sums exits non-zero with the mismatch message
and writes no registry entry.

The existing 111 tests must stay green throughout.

## Success criteria

1. A successful download-based install leaves nothing behind in the download cache
   and nothing in the system temp directory.
2. Killing an install mid-download and re-running it resumes from the bytes already
   on disk rather than restarting.
3. An archive whose SHA-512 does not match the published sums never reaches the
   install root, and the failure message says why.
4. A failed extraction leaves the install root exactly as it was, including when
   `--force` targeted an existing install.
5. Forgetting `--force` produces a two-line actionable message, not a stack trace.
6. `dotnet build` emits zero warnings across both projects.
7. The existing 111 tests still pass, alongside the new coverage in §10.
