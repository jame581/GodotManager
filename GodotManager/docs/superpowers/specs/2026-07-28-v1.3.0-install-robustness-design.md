# godman 1.3.0 — Install-Flow Robustness — Design

**Date:** 2026-07-28
**Status:** Approved, ready for implementation planning
**Baseline:** `v1.2.0` (tag == `main` == `bb89085`); 111 tests passing, 3 skipped

## Goal

A hardening release for the install flow. No new subsystems and no new platforms —
close the integrity, cleanup, and resilience gaps in the code path that downloads
and unpacks a Godot build, and clean up the surrounding drift.

## Motivation

Four defects in the current install path, all confirmed against `v1.2.0`:

1. **Temp archives leak forever.** `InstallerService.cs:376` creates the download
   target via `Path.GetTempFileName()`. Nothing deletes it — no `File.Delete` call
   anywhere in the codebase touches it. Every download permanently leaves a
   100–200 MB archive in the system temp directory.

2. **Failed extraction poisons the target directory.** `InstallerService.cs:73`
   creates `targetDir`, then `ExtractAsync` runs at line 86. If extraction throws,
   the partial directory survives with no matching registry entry, and the next
   attempt fails with "already exists. Use --force" — a dead end for the user.

3. **Checksums are computed but never verified.** SHA-256 is hashed during download
   (`InstallerService.cs:378-399`) and stored on the registry entry, but the only
   consumer is `ListCommand.cs:35`, which truncates it for display. A corrupted or
   tampered download installs silently.

4. **No retry and no resume.** A single `GetAsync`; any mid-transfer network drop
   fails the whole install and discards every byte received.

Plus two drift items: `GodotManager.Tests.csproj` lacks `<Nullable>enable</Nullable>`
(6 CS8632 warnings on every build), and CLAUDE.md points at a `manifests/j/JanMesarc/`
directory that has never existed in the repo.

## Upstream facts this design depends on

Verified 2026-07-28:

- `GodotDownloadUrlBuilder.cs:46,68` builds URLs against the
  `downloads.godotengine.org` redirector, which resolves to object storage —
  e.g. `https://godot-releases.nbg1.your-objectstorage.com/4.5.1-stable/Godot_v4.5.1-stable_linux.x86_64.zip`.
- That mirror does **not** serve `SHA512-SUMS.txt` (returns 403).
- `SHA512-SUMS.txt` **is** a GitHub release asset on `godotengine/godot-builds`:
  `https://github.com/godotengine/godot-builds/releases/download/4.5.1-stable/SHA512-SUMS.txt`
  — 29 entries for 4.5.1, standard `sha512sum` format (`<128-hex><2 spaces><filename>`).
- The filenames in that file match the redirector's resolved asset names exactly,
  so the resolved archive name is a valid lookup key.
- The sums are **SHA-512**; godman currently computes SHA-256.
- `GodotVersionFetcher.cs:22` queries `godotengine/godot` — a *different* repo from
  `godot-builds`, where the builds and sums live.

## Decisions

| Question | Decision |
|---|---|
| Verification strictness | Verify when sums are obtainable; **mismatch aborts the install**. When sums cannot be obtained (offline, `--url`, `--archive`, non-stable flavor), warn and continue. |
| Resume depth | Cross-invocation: partials persist in a managed cache dir and resume on a later `godman install` run. |
| Structure | Extract a new `Services/DownloadService.cs`; `InstallerService` keeps orchestration, extraction, and registry writes. |
| Release shape | One release, `1.3.0`. |

---

## 1. Paths

`AppPaths` gains one property:

```csharp
public string DownloadCacheDirectory { get; }   // Path.Combine(ConfigDirectory, "downloads")
```

Created in `EnsureDirectories()` alongside the existing directories. Because it hangs
off `ConfigDirectory`, it inherits `GODMAN_HOME` overriding automatically, so
`GodmanTestFixture` isolates it with no fixture changes.

## 2. `Services/DownloadService.cs` (new)

Sole responsibility: get bytes from a URI onto disk, resiliently, and report whether
they are trustworthy.

```csharp
internal enum ChecksumStatus { Verified, Unverified }

internal sealed record ChecksumSource(string Version, string Flavor = "stable");

internal sealed record DownloadOutcome(
    string FilePath,
    string ArchiveName,
    string Sha512,
    ChecksumStatus Status,
    string? UnverifiedReason);

internal sealed class DownloadService
{
    public Task<DownloadOutcome> DownloadAsync(
        Uri uri,
        ChecksumSource? checksums,     // null => not an auto-built URL
        Action<double>? progress,
        CancellationToken ct);
}
```

Dependencies: `HttpClient`, `AppPaths`, `DiagnosticContext` — the same shape as the
existing services. Registered in `Program.cs` beside `InstallerService`.

Two statuses rather than three: every non-`Verified` path (offline, `--url`,
`--archive`, sums fetch failed, filename absent from the sums file) reports
`Unverified` with a human-readable `UnverifiedReason`. One code path, one message shape.

## 3. Download cache layout

Under `<ConfigDirectory>/downloads/`, keyed by the first 16 hex characters of the
SHA-256 of the absolute request URI:

| File | Meaning |
|---|---|
| `<key>.part` | Incomplete transfer — its existence *always* means "not finished" |
| `<key>.json` | `{ url, archiveName, etag, totalBytes }` — sidecar for the `.part` only |
| `<key>.archive` | Fully transferred, awaiting extraction |

A `.archive` file is *complete*, not necessarily *verified* — an `Unverified` outcome
still produces one, because the user chose to continue. Only a checksum **mismatch**
prevents the rename, and in that case the `.part` file is deleted outright (§5).

**Lifecycle invariant.** At any moment a given key has *either* an in-flight
`.part` + `.json` pair, *or* a completed `.archive` awaiting extraction — never both,
and never a `.json` without its `.part`. Two rules enforce it:

- Renaming `.part` → `.archive` also deletes the `.json`. It describes an in-flight
  transfer and is meaningless once the transfer is done.
- `DownloadAsync` deletes any pre-existing `.archive` for the key **before** starting.
  One can survive a download that succeeded but whose install then failed; re-downloading
  is the honest choice, because reusing it would mean either re-hashing it anyway or
  trusting bytes whose provenance this run has not established.

This is deliberately *not* a content cache — a completed download is never reused to
skip a later transfer. Resume operates on `.part` only.

## 4. Resume protocol

1. Resume is attempted **only** when `.part` exists *and* `.json` loaded successfully
   *and* its stored URL matches the request URI. If the sidecar is missing, corrupt, or
   describes a different URL, the `.part` is discarded and the transfer starts from zero —
   without a sidecar there is no ETag, so a `Range` request would have no `If-Range`
   guard and could silently splice two different resources together.

   When resuming, issue `GET` with `Range: bytes=<partLength>-`, plus `If-Range: <etag>`
   when an ETag is known.
2. **`206 Partial Content`, and bytes were actually on disk** → append to `.part`. Both
   conditions matter: a server that returns an unsolicited 206 when nothing was resumed
   would otherwise send the code down the append path and open a nonexistent file for
   `FileMode.Open`, raising a `FileNotFoundException` that the retry classifier treats as
   transient — burning every attempt on a guaranteed failure. Treat 206-without-partial
   as a fresh transfer.

   SHA-512 state cannot survive a process
   boundary, so the existing partial is re-read from disk to rebuild the hash before
   appending. One extra local read, negligible against a network transfer. The re-read
   happens on *every* entry into this step, including in-process retries — always
   rebuilding from disk avoids two divergent code paths for the same operation.

   Progress reporting accounts for bytes already on disk: the percentage passed to
   `progress` is `(partLength + read) / (partLength + contentLength)`, so a resumed
   download starts partway along the bar instead of restarting at 0%.
3. **`200 OK`** → the server ignored `Range`, or `If-Range` failed because the asset
   changed. Truncate `.part` to zero and write fresh. This is correct handling, not an error.
4. **`416 Range Not Satisfiable`** → the partial is at or past the resource length.
   Discard `.part` and restart from zero.
5. On completion, verify (§5), then rename `.part` → `.archive`.

Retries wrap this entire sequence, so attempt *n+1* resumes from the bytes attempt *n*
landed. Transient failures are `HttpRequestException`, `TaskCanceledException` **not**
originating from the caller's `CancellationToken`, `IOException`, and HTTP 408, 429, and 5xx.

The backoff array holds the delays *between* attempts, so `[1s, 2s]` means **three
attempts separated by 1s and 2s**. Expressing it this way avoids an off-by-one where a
third array entry is never indexed and the documented policy disagrees with the code.

HTTP 403 and 404 must fail immediately without consuming retries. This requires care:
`EnsureSuccessStatusCode()` raises `HttpRequestException`, which is in the transient set,
so using it would make every 404 burn all three attempts. Non-transient statuses are
therefore converted to a non-retryable `GodmanException` explicitly.

## 5. Verification flow

`InstallerService` passes a `ChecksumSource` only when the URI came from
`GodotDownloadUrlBuilder`. `--url` and `--archive` pass `null`.

When a `ChecksumSource` is present, `DownloadService` fetches:

```
https://github.com/godotengine/godot-builds/releases/download/{Version}-{Flavor}/SHA512-SUMS.txt
```

parses the `<128-hex>  <filename>` lines, looks up the resolved archive name, and
compares against the SHA-512 streamed during download.

- **Match** → `ChecksumStatus.Verified`.
- **Mismatch** → delete the archive and throw. Never a warning.
- **Fetch failure, or filename absent from the file** → `ChecksumStatus.Unverified`
  with a reason; the download remains usable.

**The resolved archive name is a lookup key, not a folder name.** Verification needs the
post-redirect filename (`Godot_v4.5.1-stable_linux.x86_64.zip`) because that is what the
sums file lists. Install-folder naming must keep using the *request* URI, exactly as it
does today. For the redirector URL that `GodotDownloadUrlBuilder` produces,
`uri.LocalPath` is `/`, so `BuildInstallFolderName` falls back to its deterministic
`4.5.1-standard-linux-user` form. Feeding the resolved name into folder naming instead
would silently rename every future install directory, orphaning users' existing installs
and making `--force` create a second directory rather than replacing the first. Keep the
two concerns separate.

**Warn only when verification was attempted and failed.** An `Unverified` outcome for a
`--url` or `--archive` install is expected — the user chose a source with no published
sums — and warning about it on every such install is noise, emitted from inside an active
Spectre progress display. The always-on warning applies only when a `ChecksumSource` was
supplied and the check could not be completed.

The sums fetch gets a **single attempt with no retry**. It is a small request whose
failure is non-fatal by design, and retrying it would delay the install for no
benefit — the retry/backoff policy in §4 applies only to the archive transfer.

`ChecksumSource.Flavor` is always `"stable"` today, because `GodotDownloadUrlBuilder`
only constructs stable URLs (`GodotDownloadUrlBuilder.cs:14,46,68`). It is a parameter
rather than a constant so that adding beta/rc support later does not require reworking
this signature; implementers should not build any behavior conditional on other values.

`GodotVersionFetcher`'s use of the `godotengine/godot` repo is deliberately left
unchanged — unifying the two repos is a separate change with its own risk.

## 6. Registry change

`InstallEntry` gains two fields, and `Checksum` carries SHA-512 for new installs:

```csharp
public string? ChecksumAlgorithm { get; set; }   // null => legacy sha256; "sha512" going forward
public bool ChecksumVerified { get; set; }
```

Both additions are additive to the persisted JSON, and `System.Text.Json` ignores
unknown fields by default, so an older godman reading a newer `installs.json` still
works. Existing entries keep their SHA-256 values and read back with
`ChecksumAlgorithm == null`, which is interpreted as `sha256`. No migration step.

`ListCommand` gains a verified marker on the checksum column.

## 7. Extraction rollback

Deleting `targetDir` on failure would destroy a previously-good install whenever
`--force` is in play. Extraction therefore goes to a staging directory first.

**Staging is a sibling of `targetDir`, not of the install root.** `--path` lets the user
put a target anywhere, and `Directory.Move` fails across filesystems (`EXDEV` on Linux,
"identical roots" on Windows). Deriving staging from `Path.GetDirectoryName(targetDir)`
keeps the move same-volume by construction for *every* target, not just the default one.

**The parent chain must be created explicitly.** Today `Directory.CreateDirectory(targetDir)`
creates every missing ancestor, so `--path ~/tools/godot/4.5.1` works with no `~/tools/godot`.
`Directory.Move` requires the destination's parent to already exist, so the parent
directory has to be created before the move or that case regresses.

Two cases, because they have different safety requirements:

**Fresh install — `targetDir` does not exist.** Atomic:

1. Extract into `<parentOf(targetDir)>/.staging-<guid>`; run the Linux
   executable-permission pass there.
2. `Directory.CreateDirectory(parentOf(targetDir))`, then `Directory.Move(staging, targetDir)`.
3. On any failure: best-effort delete of staging, then rethrow. Nothing was created at
   the target, so there is nothing to roll back.

**`--force` onto an existing directory — merge, not replace.** Extract into staging as
above, then copy staging's contents over `targetDir`, overwriting file-by-file, and delete
staging. This preserves today's semantics: `--path` accepts an arbitrary directory, and a
delete-then-move would recursively destroy anything else living there. `godman install
--path ~/Godot --force` must not wipe `~/Godot`.

The trade-off is explicit: the `--force`-onto-existing case is **not** atomic, and a
failure part-way through the merge can leave that directory partly updated. Making it
atomic would require replace semantics, which costs unrelated user files — a worse
outcome than a partial update. Note also that delete-then-move is not merely non-atomic
but *actively worse than today*: if the recursive delete fails part-way (a Windows lock on
a running `godot.exe`, an AV handle), the target is already partly destroyed and the
staging copy is then thrown away by the failure path.

## 8. Cleanup ownership

- The `.archive` is deleted after a successful install — best-effort, warning only under
  `--verbose`, per the existing convention. (The `.json` is already gone by then, per §3.)
- A user-supplied `--archive` file is never deleted.

**The Windows elevated global-install path needs explicit handling.** It is the one flow
where the process that downloads is not the process that installs, and left alone it
reproduces the exact leak this release exists to close:

`InstallWithElevationAsync` resolves the plan — and therefore performs the download — in
the *parent* process, then passes the archive path to an elevated child and never calls
`InstallAsync` itself. So the parent never reaches the cleanup. The child receives a
non-null `InstallPath`, takes the local-archive branch, and so has no `CacheFilePath` to
clean either. Every `godman install --scope Global` on Windows would orphan a 100–200 MB
`.archive` in `%APPDATA%\godman\downloads\` — a directory `doctor` now reports on.

Two consequences to fix together:

1. The **parent** deletes the cache entry after the elevated child exits successfully.
   It owns the download, so it owns the cleanup.
2. The parent's verification result must reach the registry. The child currently re-hashes
   the archive locally and records `ChecksumVerified = false`, so a global Windows install
   would never show as verified even when the parent verified it. `ElevatedInstallPayload`
   carries the checksum, its algorithm, and the verified flag, and the child records those
   rather than recomputing.
- `clean` removes the entire downloads directory.
- `doctor` reports the downloads directory size and stale-partial count, so an
  abandoned 200 MB `.part` is discoverable.

## 9. Error handling

**Correction to an earlier draft of this spec.** It claimed that `Program.cs:68` routes
every failure through `AnsiConsole.WriteException` and that forgetting `--force` yields a
.NET stack dump. That is false, and the design must not be justified by it. Verified
against Spectre.Console.Cli 0.55.0: `CommandApp` catches command exceptions internally
and returns `-1` unless `config.PropagateExceptions()` is set, which `Program.cs` never
calls — so both top-level catches at `Program.cs:61-70` are already unreachable for
command failures. On top of that, `InstallCommand.cs:89-92` and `FetchCommand.cs:89-93`
each wrap their whole body in `catch (Exception ex) { return Fail(ex.Message); }`.

What a user actually sees today is a clean one-liner: `Install failed: <message>`.

So the real defect is narrower than claimed, and the fix is different. The message is
fine; what is missing is the **actionable half** — those catch-alls print `ex.Message`
and discard everything else, so there is nowhere for a remedy to live.

Introduce `Infrastructure/GodmanException.cs` for expected, user-actionable failures,
carrying an optional hint. The rendering must happen where the exception is actually
caught:

- `InstallCommand`, `FetchCommand`, and `ElevatedInstallCommand` each gain a
  `catch (GodmanException)` **before** their existing catch-all, printing the message and,
  when present, a `hint:` line.
- `Program.cs` keeps a matching catch for anything thrown outside the command pipeline.
  It is defence in depth, not the primary path — and the spec must not claim otherwise.

Adding `config.PropagateExceptions()` was considered and rejected: it would route every
command failure through `Program.cs`, discarding the per-command `Install failed:` /
`Fetch failed:` prefixes that give errors their context, in exchange for centralising a
rendering that the per-command catches already do correctly.

Sites addressed:

| Site | Problem | Fix |
|---|---|---|
| `InstallerService.cs:70` | "already exists. Use --force" — dead end; doesn't say whether a registered install owns the directory | Report whether a registry entry owns it; offer `--force` vs `godman remove <id> --delete` |
| `GodotVersionFetcher.cs:156` | "Failed to fetch releases from GitHub: …" — no recourse offered | Distinguish rate-limit from offline; mention the stale-cache fallback and `--no-cache` |
| `InstallerService.cs:83,213` | Internal invariants leaking to users | Leave as unexpected exceptions — these firing means a bug |
| `ActivateCommand.cs:75,80,133,148`, `CleanCommand.cs:100,115` | Already clear and actionable | Unchanged |

New failure modes get first-class messages:

- **Checksum mismatch** — names expected and actual hashes, the sums URL, and states
  that the archive was deleted.
- **`Unverified`** — an always-on warning, not `--verbose`-gated, but only when
  verification was attempted and failed (§5). A skipped integrity check is moderate-risk,
  matching the precedent recorded in PLAN.md:112.
- **Rollback** — when extraction fails, the message states that no partial install was
  left behind. This is user-facing text, not just a silent `throw`, and needs a concrete
  home in the implementation rather than an aspiration here.

## 10. Testing

`MockHttpHandlers` gains three reusable capabilities:

- `Range`-aware responses returning 206 with a correct `Content-Range`
- a mode that deliberately ignores `Range` and returns 200
- sequenced responses, so "fail twice then succeed" is expressible

New `DownloadServiceTests`:

- resume sends `Range: bytes=<n>-`, and the completed file matches the full expected content
- **after a resume, `outcome.Sha512` equals the SHA-512 of the whole payload.** Rebuilding
  hash state from bytes already on disk is the subtlest code in the release; without this
  assertion a rehash bug ships green and surfaces as a spurious `ChecksumMismatchException`
  on every real resumed download
- a resumed download combined with a `ChecksumSource` still reports `Verified`
- **the progress test must use a payload larger than the 80 KB read buffer.** With a
  payload smaller than one buffer there is exactly one read, so a correct implementation
  and one that ignores resumed bytes both report `[100, 100]` and the test passes either way
- a `.part` whose `.json` sidecar is missing or names a different URL restarts from zero
  and sends no `Range` header
- an unsolicited 206 with no `.part` on disk is treated as a fresh transfer, not an append
- server returns 200 despite `Range` → partial truncated, result still correct
- 416 → discard and restart
- transient 5xx twice then success → one `DownloadOutcome`, backoff honored
- 404 → fails immediately, no retries consumed
- sums match → `Verified`
- sums mismatch → throws, **and** the archive file is gone
- sums fetch fails → `Unverified` with a reason, download still usable
- `null` `ChecksumSource` → `Unverified`, and no request is made to the sums URL

`InstallerServiceIntegrationTests` additions:

- extraction failure leaves no `.staging-*` directory and no `targetDir`
- extraction failure under `--force` leaves the pre-existing install intact
- successful install removes `.archive` and `.json` from the download cache
- a user-supplied `--archive` file still exists after install

Coverage that must exist end-to-end, not only at unit level. Every existing CLI and E2E
install test passes `--url` or `--archive`, so the auto-URL path — the only one that
supplies a `ChecksumSource` — is currently exercised by nothing. Inverting the condition
that decides whether to verify would not fail a single test. Required:

- install with mismatched sums exits non-zero with the mismatch message and writes no
  registry entry
- a verified install records `ChecksumVerified = true` and `list` renders its marker
- an attempted-but-failed verification emits the always-on warning; a `--url` or
  `--archive` install does **not**
- `--path` into a directory whose parent does not exist still succeeds
- `--force` onto a directory holding an unrelated file leaves that file in place

The existing 111 tests must stay green throughout. Two of them encode SHA-256 assumptions
(`InstallerServiceIntegrationTests.cs:60,102` assert a 64-character hash, and `:105`
computes one) and must be updated to SHA-512 rather than weakened.

## Success criteria

1. A successful download-based install leaves nothing behind in the download cache
   and nothing in the system temp directory.
2. Killing an install mid-download and re-running it resumes from the bytes already
   on disk rather than restarting.
3. An archive whose SHA-512 does not match the published sums never reaches the
   install root, and the failure message says why.
4. A failed extraction leaves the install root exactly as it was, including when
   `--force` targeted an existing install.
5. Forgetting `--force` produces the existing `Install failed:` line *plus* a `hint:` line
   naming the concrete remedy, and that hint survives all the way to the terminal — not
   just to the exception object.
6. `dotnet build` emits zero warnings across both projects.
7. The existing 111 tests still pass, alongside the new coverage in §10.
